# Codex Judge 依頼テンプレート（敵対的モード・実装コード）

敵対的モード（`--codex-advs-review-loop` / セキュリティ自動発動）のループで、Breaker（独立 Fable エージェント。Workflow 不能時はメインセッションが代行）が生成した反例を Codex（Judge）に裁定させる依頼文のテンプレート。`<>` を埋めて、**Claude Code ホスト**では `codex:rescue` へ task として渡し、**Codex CLI ホスト**（本 skill 自体を Codex CLI が実行している場合。`codex:rescue` は存在しない）では `codex exec` の入力として渡す。標準モードのレビュー依頼は [codex-review-prompt.md](codex-review-prompt.md) を使う。

---

## Codex への依頼文テンプレート（codex:rescue / codex exec 共通）

```
あなたは GitHub Issue 対応の実装コードの Judge（裁定者）として振る舞う。
別の AI（Breaker）が生成した反例・攻撃シナリオを、リポジトリの実コードと照合して裁定するのが目的である。
Breaker に迎合せず、独立した視点で判断すること。

## 入力

### 1. Issue の要件
<Issue のタイトル・要件・受け入れ基準の要約>

### 2. 実装計画（あれば）
<smart-issue-plan が作成した計画の実装手順・影響範囲の要約。計画がない場合はこのセクションを省略する>

### 3. レビュー対象（ラウンド N）
現在ブランチ <ブランチ名> の変更全体を対象とする。diff の基準は次の通り:

- コミット済み変更: `git diff origin/<デフォルトブランチ>...HEAD`
- 未コミット変更: `git status` / `git diff`（working tree に残っている変更も対象）

ローカル <デフォルトブランチ> は origin より古いことがあるため、必ず `origin/<デフォルトブランチ>` を基準にすること。

### 4. Breaker の反例リスト
<Breaker（独立 Fable エージェント）が列挙した反例・攻撃シナリオ・不変条件違反。各項目に、対応する反例テストがあればその実行結果（fail / UNVERIFIED。pass した仮説は Breaker が破棄済みのため現れない）を併記する>

### 5. 前ラウンドからの変更点（2 ラウンド目以降のみ）
<採用した指摘と反映内容の要約。初回ラウンドではこのセクションを省略する>

### 6. プロジェクト固有基準（あれば）
<呼び出し側が収集したプロジェクト固有のコーディング規約・レビュー基準の要点（アーキテクチャ層責務・DB/トランザクション・性能・テストカバレッジ・セキュリティ等）。なければこのセクションを省略する>

## 裁定タスク

1. Breaker の各反例を、リポジトリの実コードと照合して次の 4 カテゴリに分類する:
   - **真の欠陥**: 仕様違反・セキュリティリスク・回帰・運用/保守/可用性の欠陥（可観測性・デプロイ/ロールバック・過度な結合・タイムアウト/リトライ・障害時の劣化・単一障害点など）・データ整合性/性能（トランザクション境界・冪等性・N+1・計算量）・テストカバレッジ不足・アーキテクチャ層責務の逸脱・プロジェクト固有基準違反として妥当で、修正価値がある
   - **仕様未定**: 仕様が曖昧で、Breaker が勝手な前提を置いている（要仕様確認）
   - **低優先度**: 妥当だが重大度が低く、修正コストに見合わない
   - **ノイズ**: 反証不能・誤解・的外れ（除外）
2. Breaker が見落とした欠陥があれば、独立レビューとして追加で挙げる（同じ 4 カテゴリで分類する。「6. プロジェクト固有基準」の提示があれば、それとの不整合も照合対象に含める）
3. 各指摘に、分類理由・根拠（ファイルパス・行番号など一次情報）・重大度（High / Medium / Low）・修正コスト見積（S / M / L）を付ける

## 制約

- 可読性・命名・スタイルの指摘は対象外（修正価値のある欠陥のみ）
- 「真の欠陥」は次の 4 点に答えられるものだけにする: (1) 何が起きるか (2) なぜそのコードパスが脆弱か (3) 想定される影響 (4) リスクを下げる具体策。答えられない懸念は低優先度またはノイズに分類する
- 弱い指摘を複数並べるより、根拠を防御できる強い指摘を優先する。重大な指摘を些末な指摘で薄めない
- コードやファイルの変更は行わない（裁定のみ）
- 真の欠陥・仕様未定が 1 件もなければ「指摘なし」とだけ返す

## 出力フォーマット

### Judge 裁定結果（ラウンド N）

#### 真の欠陥
##### 指摘 1: <タイトル>
- 重大度: High|Medium|Low ／ 修正コスト: S|M|L
- 根拠: <ファイルパス・行・確認方法>
- 分類理由: <なぜ真の欠陥か>
- 内容: <何が起きるか・なぜ脆弱か・想定影響・どう直すべきか>

#### 仕様未定
（確認が必要な前提と、Breaker が置いた仮定を列挙）

#### 低優先度 / ノイズ（件数と 1 行タイトルのみ）
（採用対象外。監査性のため件数と理由を残す）

（真の欠陥・仕様未定がない場合は「指摘なし」とだけ書く）
```

## 呼び出し時の注意

- このテンプレート全体を埋めたうえで渡す。**Claude Code ホスト**では Skill ツールの `codex:rescue` に task として渡す。**Codex CLI ホスト**（本 skill 自体を Codex CLI が実行している。`codex:rescue` は存在しない）では `codex exec` を起動する — 具体的な起動手順・失敗時の診断は [codex-review-prompt.md](codex-review-prompt.md) の「Codex CLI ホストでの補足」に必ず従う（ホストのサンドボックス内では起動できない・stdin リダイレクト漏れで無応答になる等、既知の落とし穴がある）。いずれの経路でも、Breaker を実施したセッションとは独立した新規セッションで裁定させる
- Codex はリポジトリにアクセスできるため、diff の取得・コードの確認・反例の照合は Codex 側に行わせる（巨大な diff や反例テスト全文を依頼文に貼り込まない。要点のみ）
- Codex にコードの修正を行わせない（裁定のみ）。修正は Claude 側の妥当性判定（過剰対応チェック）を経てから行う
- 返ってきた裁定の再解釈・要約による弱体化をしない（妥当性判定は採用 / 不採用の分類と理由の明記のみ）

## 運用ノート: silent death（ハング・静止死）からの復旧

silent death の検知・回収・復旧（cancel → `--resume` 再投入）・予防の手順（Claude Code ホスト / codex:rescue 経由）、および Codex CLI ホストでの補足は [codex-review-prompt.md](codex-review-prompt.md) の「運用ノート」に従う。復旧を 2 回試しても完了しない場合は、SKILL.md の「フォールバック（codex:rescue / codex exec が利用不能時）」に切り替える。
