# Jira チケット起点（smart-issue-plan）

引数が Jira キー / Jira URL のとき、または `#N` で指定した Issue が Jira 起点の計画 Issue だったときに、SKILL.md の該当手順から参照する。手順番号は SKILL.md のもの。

> **同期ノート**: 「共通規則」節は `smart-issue-resolve/references/jira-input.md` と同一文面（スキル間でファイルを参照できないための意図的な二重化）。resolve は plan が書く書式（タイトル接頭辞・本文冒頭・要件基準の正規化）を読むので、片方だけ変えない。変更時は CLAUDE.md「Jira 入口規則の二重化」に従い両方を同期する。

## 共通規則

### 入力判定

フラグを除去し `-p` で分割した後の対象トークンから、先頭の `#` を除いて判定する。

- `^[0-9]+$` → GitHub Issue 番号
- `^[A-Z][A-Z0-9_]+-[0-9]+$` → Jira キー
- `http(s)://` で始まり、パスに `/browse/<キー>` またはクエリに `selectedIssue=<キー>` を含む → Jira URL（ホストがサイト。キーは上の形式に合うこと）
- どれにも当たらない（例: `proj-123`）→ ユーザーに確認する

### Atlassian MCP の使い方

ツール名はフルネームで決め打ちしない。MCP の版によって名前が異なるため、次の相当品を使う。ツールが遅延読み込みされる環境では、検索してから不在と判断する。

- 課題取得: `getJiraIssue` 相当
- コメント追加: `addOrEditJiraIssueComment` / `addCommentToJiraIssue` など
- アクセス可能サイトの一覧: `getAccessibleAtlassianResources` 相当

`cloudId`:

- URL 入力なら、サイト URL をそのまま `cloudId` に渡す（現行の 2 版とも、スキーマ上サイト URL を受け付ける）
- キーだけの入力、または `#N` 入力で、計画 Issue 本文の `> 元チケット:` 行に URL があれば、そのサイト URL を使う（plan が正規形で書いた行で、サイトが確定している）
- 上のどちらも無い、またはサイト URL で失敗した場合に限り、サイト一覧を取得する。1 件ならそれを使い、複数ならユーザーに選ばせる

取得項目:

- サマリ・説明・ステータス（statusCategory）・`updated`・ラベルを取得する
- 既定ビューで `updated` や statusCategory が欠けていたら、フィールドを指定して取り直す。推測で埋めない
- Jira のステータス遷移とリモートリンク（Web links）は使わない

**MCP が使えないとき**: ツールが無い・未認証・`cloudId` を解決できない・呼び出しが失敗する、のいずれも「使えない」とみなす。plan は停止して選択肢（中止 / 要件を貼り付けて続行）を出す。resolve は要件更新の検知を「未実施」と明示して続行する。

### 確定書式

plan が書き、resolve が読む。変更しない。元チケットのリンクは `https://<site>.atlassian.net/browse/<キー>` の正規形で書く（入力 URL がボード URL などでも、この形に直す）。

```
■ Issue タイトル
[実装計画][PROJ-123] OAuth ログインを追加する

■ Issue 本文冒頭
> 元チケット: [PROJ-123](https://<site>.atlassian.net/browse/PROJ-123)（Jira）
> 要件の正本は Jira チケット。以下は計画作成時点の要約
> 要件基準: Jira updated 2026-10-23T15:04:05+09:00

### 要件の要約
- ...（1〜5 行）

## 実装計画
> 対象チケット: PROJ-123（Jira）
> 分析時点: `abc1234`（2026-10-23）
...

■ Jira コメント（Markdown）
GitHub に実装計画 Issue を作成しました: owner/repo#45
https://github.com/owner/repo/issues/45
（計画の正本は GitHub Issue 側。smart-issue-plan で作成）
```

### Jira 起点の計画 Issue

対象 Issue 自身が次のどちらかを満たすもの。入力が `#N` でも、この判定に当たれば Jira 起点として扱う。

- タイトルが `[実装計画][<キー>]` で始まる
- 本文冒頭に `> 元チケット: [<キー>](<URL>)（Jira）` 行がある

キーと URL は本文の行から読む。行が無ければキーはタイトルから取り、URL は入力 URL かサイト一覧から組み立てる（得られなければリンクなしでキーだけ書く）。

Issue のタイトル・本文から読んだ値は、検索や `date` のコマンドに埋め込む前に形式を検証する（他者が書式をまねた Issue でも、不正な文字列をシェルへ渡さないため）。キーは入力判定と同じ `^[A-Z][A-Z0-9_]+-[0-9]+$`、「要件基準」の時刻は `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}[+-][0-9]{2}:[0-9]{2}$` に一致するときだけ使う。一致しなければ「読めない」として扱う（キーなら Jira 起点とみなさない・時刻なら要件基準行が読めない扱い）。

### 計画 Issue の検索

1. 対象は現在の作業ツリーの origin（owner/repo）だけ。1 チケット × 複数リポジトリの専用処理はしない。入力が `#N` で入った場合は、N を完全一致の集合に必ず含める（検索がヒットさせなくても N は存在する。以降の検索は N 以外の重複を探すためだけに使う）
2. GitHub MCP の Issue 検索（`search_issues`）を呼ぶ。この検索は semantic 検索なので、query はキー、owner/repo を指定し、fields は number・title・state・html_url・created_at に絞る
3. タイトルが `[実装計画][<キー>]` で始まるものだけ残す。閉じ括弧 `]` まで含めて照合するので、`PROJ-1234` は混ざらない。open / closed の両方を対象にする
4. 次の場合は、読み取り専用の `gh issue list --repo <owner>/<repo> --state all --search '"<キー>" in:title' --json number,title,state,url --limit 50` で裏取りし、同じフィルタを掛ける: MCP が使えない・エラーになった、または 3 で 0 件になった（semantic 検索の 0 件は不在の証明にならない）
5. gh も使えなければ「検索で確定できない」状態とし、次の表の「確定できない」行に従う。0 件とはみなさない

### 検索結果の扱い

件数は、open と closed を合わせた完全一致の件数。

| 完全一致の件数 | plan | resolve |
|---|---|---|
| 0 件 | 新規作成 | `/smart-issue-plan <キー>` を案内して終了。作成直後は検索インデックスへの反映が遅れうるので、`#<計画Issue番号>` で直接実行する選択肢も添える |
| 1 件（open） | 更新モードへ | その Issue で続行 |
| 1 件（closed） | ユーザーに確認（再オープンして更新 / 新規作成 / 中止） | その Issue で手順 1 へ進み、既存のクローズ判定で終了する（`/smart-issue-plan <キー>` を案内する） |
| 2 件以上 | ユーザーに確認（更新する Issue を選ぶ〔closed なら再オープンして更新〕/ 新規作成 / 中止） | どれで続行するかユーザーに確認 |
| 確定できない（検索が使えない・失敗） | ユーザーに確認（中止 / 新規作成 / 既存の計画 Issue 番号を指定）。確認なしに新規作成しない。レビューループのフラグを指定していても確認する | ユーザーに確認（中止 / 計画 Issue 番号を指定） |

### 要件基準の時刻

- **記録**: Jira が返した `updated` を、秒精度・`±hh:mm` に正規化して書く。小数秒は切り捨て、`+0900` は `+09:00`、`Z` は `+00:00` にする。タイムゾーンの換算はせず、Jira が返したオフセットのまま書く
- **比較**: 現在値も同じ規則で正規化し、時刻として比較する。正規化前の文字列同士は比較しない
  - 両辺のオフセットが同じなら、正規化後の文字列の大小が時刻の前後と一致する
  - オフセットが違えば、コマンドで epoch 秒に換算して比較する。BSD/macOS は `date -j -f '%Y-%m-%dT%H:%M:%S%z' '<オフセットのコロンを除いた値>' +%s`、GNU は `date -d '<値>' +%s`
  - 換算できなければ「比較不能」と伝える
- **判定**: 現在値 > 記録値なら更新あり、等しければ更新なし、現在値 < 記録値なら比較不能

## plan 固有の手順

### 1-J 読み取り（手順 1 の代わり）

- 課題が無ければ通知して終了する。statusCategory が done なら通知して終了する。説明が空ならユーザーに確認する
- 正規化した `updated` を U1 として保持する
- 以降の手順にある「Issue のタイトル・本文・ラベル」は、Jira のサマリ・説明・ラベルに読み替える（探索、セキュリティ自動発動の判定、レビュー基準）。外部リンクの扱いは手順 1 と同じ
- 入力が `#N` で、手順 1 で読んだ Issue が Jira 起点の計画 Issue だった場合は、そのキーで 1-J からやり直す（計画 Issue 自体を計画してしまうのを防ぐ）。この判定は手順 1 のクローズ済み判定より先に行い、クローズ済みの計画 Issue は終了せず「検索結果の扱い」の closed の行（再オープンして更新 / 新規作成 / 中止）に進む

### 2-J 重複防止（手順 2 の代わり）

共通規則の「計画 Issue の検索」と「検索結果の扱い」に従う。

- 更新モードなら手順 8 と 8-J に入る。再オープンを選んだ場合は、`issue_write` で open に戻してから更新モードに入る
- 新規作成なら手順 3 を飛ばし、常に「新規 Issue」とする

### 5-J 計画作成の読み替え

- `plan-template.md` の対象行は `> 対象チケット: <キー>（Jira）` にする
- 推奨ブランチ名は、プロジェクト独自の規則が無ければ `{type}/issue-<計画Issue番号>-{キー小文字}-{説明}`（例: `feature/issue-<計画Issue番号>-proj-123-add-oauth-login`）にする
  - `<計画Issue番号>` は、投稿後に確定値へ書き戻すプレースホルダ
  - キー部分に限り `_` を残す。キーを変形すると Jira 側の紐付けの前提が崩れるため。小文字キーが Jira の開発パネルで紐づくかは未検証
- 次のアクションは `/smart-issue-resolve <キー>`（または `#<計画Issue番号>`）にする
- 本文冒頭の 4 要素（元チケット・要件の正本の注記・要件基準・要件の要約 1〜5 行）は投稿時に付ける。`plan.md` は従来どおり `## 実装計画` 以降だけ

### レビューループの実行時

- `context.md` の見出しと `{作業Dir}` 名の `<番号>` は、Jira キーで代用する（更新モードも同じ）
- Workflow の `args.issueNumber` には、新規作成なら Jira キー、更新なら計画 Issue 番号を渡す。雛形での使用箇所はプロンプト文だけなので、「GitHub Issue #PROJ-123」と表示されるのは見た目の問題にとどまる
- `context.md` の「追加指示」に「`<計画Issue番号>` は投稿後に確定値へ書き戻すプレースホルダで、指摘・修正の対象外」と書く
- codex 系テンプレートの「Issue の要件」欄には Jira の要件を入れる（テンプレートは変えない）

### 6 プレビュー

Jira 起点では、タイトル・本文冒頭・Jira に投稿するコメント文もあわせて提示する。

### 7-J 投稿（手順 7 の新規 Issue の代わり）

この順で行う。

1. 作成直前に `updated` を取り直す（U_pre）。U1 と異なる、または取得に失敗した場合は「計画作成中に Jira が更新された可能性がある」と通知する。その場合、手順 5 の書き戻しでは要件基準を U1 のまま残す（あとで resolve が検知する。計画作成中のレビューループ中の更新が書き戻しで隠れるのを防ぐ）
2. `issue_write` で作成する。タイトルは `[実装計画][<キー>] <Jira サマリ>`。本文は、本文冒頭（要件基準は U1）、計画、レビュー済み表記の順
3. Jira に**通常コメント**を投稿する。文面と改行は確定書式どおり、形式は Markdown
4. `updated` を取り直す（U2）。自分のコメントで `updated` が進むため、作成前の値を記録すると resolve が毎回誤警告する
5. `issue_write` の更新を 1 回だけ行う。更新は本文全体の置換なので、手順 2 で作成した本文全体を再送する。置き換えるのは要件基準行（U2。手順 1 で差分ありなら U1）と、`<計画Issue番号>` のすべての出現だけ。本文冒頭とレビュー済み表記を落とさない
6. 完了案内として、Issue の URL と `/smart-issue-resolve <キー>`（または `#<計画Issue番号>`）を示す。手順 1 で差分があった場合は、`/smart-issue-plan <キー>` での更新も勧める

失敗したとき:

- 手順 2 が失敗 → Jira には何もせず終了する
- 手順 3 が失敗 → コメント文面を提示して手動投稿を頼み、手順 4・5 は実施する
- 手順 4 が失敗 → U1 のまま手順 5 を実施する
- 手順 5 が失敗 → 本文には U1 とプレースホルダが残る。resolve が 1 回警告する安全側の状態である旨を伝える

### 8-J 更新モード（手順 8 に加える）

- 8a で、1-J の U1 と本文の要件基準を比較する。更新されていれば、Jira の要件と本文の「要件の要約」を突き合わせて変更点を特定する
- 8c の本文更新で、要件の要約と要件基準（U1）を書き直す。本文冒頭が無ければ確定書式で補う
- Jira へのコメントは再投稿しない。リンクは作成時に投稿済みで、再投稿すると `updated` が進み、もう一度書き戻しが要るため
- タイトルの接頭辞 `[実装計画][<キー>]` は変えない。サマリ部分は Jira に合わせる

### MCP 不在のまま、貼り付けで続行する場合

- GitHub 側の重複確認は行う
- キーだけの入力なら URL も求める
- ステータスの確認は未実施と明記する
- 要件基準行は `> 要件基準: 未取得（Atlassian MCP 不在のため要件はユーザー貼り付け）` とする（resolve は「読めない」として扱う）
- Jira コメントは投稿せず、文面を提示する
