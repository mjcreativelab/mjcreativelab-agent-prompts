# 文書の種類ごとの部品

SKILL.md 3 章の部品を、文書の種類ごとに具体化したもの。（ ）付きの部品は、条件を満たすときだけ置く。見出し名は例で、プロジェクトの慣習があればそちらに合わせる。

## Design doc・設計書・ADR の本文

1. `## 結論` — 採用した設計と理由（3 文以内）。直後に関連 Issue へのリンク
2. `## 検討した代替案` — 設計で選んだ箇所（パターン・置き場所・データの持ち方など）ごとに、比べて捨てた案を `| 案 | 採らなかった理由 |` で。他人の決定を文書にするときは、素材にある案だけを載せる
3. `## 設計` — 結論を支える中身。構成（図やツリーは全体像がつかめる粒度で）、処理の流れ、要件の曖昧な点について決めたこと（表: `| 論点 | 決定 | 理由 |`）
4. `## やらないこと` — 依頼の隣にあるが扱わないもの（保存・API・画面・運用など）を 1〜5 項目
5. `## 未決事項`（あるとき）— 誰に何を確認するか、答えが変わったときに直す箇所
6. `## テスト・検証` — 実装前ならテストの方針、実装後なら実行結果
7. `## リスク`（この設計に固有で、対策が決まっているものがあるとき）

ADR で見出しの順序が決まっているとき（Context → Decision → …）は、タイトルを決定の文にする。

## PR 本文

1. 冒頭（見出しなし）— 何を・なぜ変えたか（1〜3 文）と、Issue・Design doc へのリンク
2. `## レビューで見てほしい点` — diff からは読み取れない意図・懸念・確認してほしい箇所を、箇所（ファイル・関数）と観点の組で
3. `## 検証` — 実行したコマンドと結果
4. `## マージ前に必要なこと`（あるとき）— 確認待ち・マージの順番など。詳細が Design doc にあれば節へのリンクで示す

変更ファイルの一覧と Design doc の中身は、diff とリンク先で読めるので PR 本文には置かない。

## Issue・提案書

1. 何を依頼・提案するか＋なぜ（1〜3 文）
2. 現状の問題 — 事実と、分かるなら数値
3. 提案する内容・進め方
4. 完了の条件 — 検証できる形で
5. やらないこと（読み手が範囲内と思いそうな境界があるとき）

## 報告書・調査結果・振り返り

1. 結論 — 分かったこと＋次の行動・依頼（3 文以内）
2. 根拠 — データ・事実と出典
3. 前提と調べ方（結論の確からしさに関わるとき）
4. 未確認のこと（あるとき）

## 議事録

1. 決まったこと
2. やること — 担当・期限
3. 決まらなかったこと（あるとき）— 次にどうするか
4. 議論の要点 — 決定の理由として残すものだけ

発言の時系列の記録は置かず、必要なら録画や原文へのリンクで示す。

## README・手順書

1. この手順で何ができるか＋前提（必要なもの・権限）
2. 手順 — 番号付きで 1 手順 1 操作。コマンドはコードブロックに入れ、成功したときに見えるもの（出力・画面）を添える
3. つまずきやすい点（実際に起きたものがあるとき）— 症状と対処
4. 次に読むもの（あるとき）— リンク

手順・コマンド・設定値は、1 つ欠けても読み手が作業をやり遂げられないので、仕上げで削る対象にならない。

## 発表資料（スライドの原稿）

1. 表紙の次に結論のスライドを置く
2. 各スライドのタイトルは、そのスライドの結論の文にする（「売上推移」ではなく「売上は 3 か月続けて減った」）
3. 1 枚に 1 メッセージ。根拠の図表は 1 枚に 1 つ
4. 目次・背景のスライドは、聞き手が前提を知らないときだけ置く
