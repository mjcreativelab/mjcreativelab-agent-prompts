# 実装ノート: human-facing-doc-writing スキル追加（Issue #148）

日付: 2026-09-30（JST）

人間が読む文書を「結論が先頭・代替案は 2 列の表・定型の節を埋めない」形で書く・書き直すスキルを追加した。元資料は Qiita 記事「[生成AIが書いたドキュメントを読みたくない](https://qiita.com/take-yoda/items/e5d9ce6618523af1ffc5)」（記事内のスキル名は `design-and-ship`）。スキルなし／ありのサブエージェントを同じ課題で比べ、手直し後の版では新規の Design doc が 203〜306 行から 75〜84 行になり、書き直し・手順書でも決定事項と手順が欠けないことを確かめた。

## 自分で判断した事項

- **名前 `human-facing-doc-writing`**: ユーザー指定（「資料を書くときは常にこのスキルを使いたいので『人間向けのドキュメント作成』のような名称に」）の直訳。「人間向け」と名前に入れることで、AI 向けの指示文書（CLAUDE.md / SKILL.md / プロンプト）を対象外にする境界も示せる
- **自動起動あり（`disable-model-invocation` を付けない）**: 記事の結論は「指示に書かない限り AI は網羅に倒れる」で、文書を書く場面で毎回読み込まれることが効果の前提になる。ガイド型スキル（software-architect・security-auditor）の前例に合わせた。副作用は `allowed-tools` を読み取り系だけにし、書き直しの上書きを承認制にして抑えた
- **対象を記事の Design doc / PR から、人間が読む文書全般へ広げた**: 「常に使いたい」に合わせた。手順書で手順が削られないよう、削る判定を「これがなくても読み手は目的を果たせるか」に結びつけた（例外条項ではなく判定基準の側で守る）
- **穴埋めテンプレート（assets/）を作らない**: 記事の「見出しを律儀に埋める」癖を呼ぶため。種類ごとの形は references/doc-shapes.md に「部品・順序・置く条件」として書いた
- **指示は禁止リストでなく「部品と順序」で書く**: superpowers:writing-skills の知見（出力の形の問題には、禁止より「出力はこの部品をこの順で持つ」という形が効く）に従った。条件は観測できる述語（「自分で設計したなら」「Design doc では」）で書いた
- **記事の文面は写さない**: 規則は自分の言葉で書き直し、README に記事と検証リポジトリ（MIT License）を参考として載せた。テストに使った記事の Before 版 Design doc などはスクラッチパッドにだけ置き、コミットしていない

## 記事からの変更・調整

- 代替案の表を 2 列（案 / 採らなかった理由）に固定した。スキルなしの書き直しで、採らなかった案の「利点」列が残ったため
- 「用語定義は必要な場合のみ」を「読み手が知らない語だけを、初めて出てくる文の中で補う（節を作らない）」にした
- 書き直しモードを加えた（ユーザーの選択）。決定・数値・手順は残し、元の文書にない主張は足さず、削る一覧の承認を得てから上書きする
- 「やらないこと」は記事どおり Design doc では必ず置く。ほかの文書では、読み手が範囲内と思いそうな境界があるときだけ置く

## テストと検証

同じ課題を、スキルなし（対照）とスキルあり（SKILL.md のパスを渡して読ませる）のサブエージェントに与えて比べた。課題は、記事と同じクーポン要件の Design doc と PR 本文、記事の Before 版 Design doc（284 行・8521 文字・見出し 32）の書き直し、手順書（README）、他人の決定（Slack スレッド）の Design doc 化。スキルの版は 3 つある: v1 は初版、v2 は代替案と「やらないこと」の条件を直した版、v3 は最終版（中身がまるごと素材にない部品を未決事項へ回す）。

| 課題 | スキルなし | スキルあり |
|---|---|---|
| Design doc 新規 | 203 / 306 行、見出し 16 / 22 | v1: 69 / 60 行（1 本で代替案と「やらないこと」が欠落）。v2: 84 / 75 / 79 行、見出し 9〜10（79 行は Sonnet） |
| 同（記事 Before 版の「詳しく丁寧に」指示つき） | 585 行・20974 文字・見出し 44 | v1: 81 行・3507 文字・見出し 11 |
| PR 本文 | 2189〜2477 文字。ファイル一覧と Design doc の内容の繰り返しあり | v1・v2 の 6 本で 495〜960 文字。どちらもなし |
| 書き直し | 123 行・5032 文字。要件の書き写し・用語集・拡張性の表が残る | v1: 65 / 74 行。v3: 66 行・3243 文字・見出し 7。3 本とも決定 12 項目をすべて保持し、創作なし |
| 手順書 | 114 行 | v1: 75 行。v3: 71 行。どちらも手順とトラブルの対処をすべて保持 |
| 他人の決定の Design doc 化 | — | v2: 37 行（中身が TODO だけの節が 2 つ）。v3: 24 行（未決事項の 1 行に） |

- スキルなしの Design doc には、結論の前にメタ情報や依頼の言い直しが来る・Issue の要件を書き写す・DDD 用語の解説を置く・代替案の表が 3〜4 列、という癖が出た。スキルありの 19 本（Design doc と書き直し 11、PR 本文 6、手順書 2）は、すべてタイトルの直後に結論が来た
- v1 → v2: 新規 Design doc で「検討した代替案」と「やらないこと」の有無が回によって揺れた（2 本中 1 本で両方なし）。エージェントが「実際に比べた案」を「素材（Issue）にある案」と狭く読んだため。「自分で設計したなら、設計で選んだ箇所ごとに比べた案がある」「Design doc では『やらないこと』を置く」に直し、他人の決定を文書にするときは素材にある案だけを載せる条件を加えた。v2 の 3 本すべてで両方が出て、他人の決定の課題では素材にない案や境界を足さなかった
- v2 → v3: 他人の決定の課題で、中身が `TODO: 未確定` だけの節が 2 つできた。「部品の中身がまるごと素材にないときは、節を置かず未決事項に 1 行で入れる」を加え、書き直し・手順書・他人の決定の 3 課題を v3 で再テストした
- v3 の書き直しでは、元の文書の「今後の拡張性」（新しい種別・条件・複数通貨）が「やらないこと」に言い換えられた。元の文書に根拠があり、承認依頼の一覧にも示されていたため許容した。元の文書にまったく手がかりがない場合は、未決事項に「やらないことは未定」が加わる可能性がある（承認依頼の一覧に出るので、ユーザーが止められる）
- 自動起動: v3 を Claude Code にグローバルインストールし、スキル名も規則も伝えない依頼（「設計書を書いて」「報告にまとめて」）をサブエージェントに与えた。2 体とも自分から Skill ツールで human-facing-doc-writing を読み込み、結論が先頭・代替案が 2 列の表の文書を書いた（設計書は 96 行）
- `mise exec node -- npx skills add ./ --list` で検出を確認した（25 skills、human-facing-doc-writing を含む）

## ユーザーが把握しておくべきこと

- 自動起動は、スキルの説明文と依頼内容の一致で決まる。上の確認では読み込まれたが、確実に使うには、グローバルの CLAUDE.md / AGENTS.md への 1 行追加が確実（README に記載）
- 今回は変更していないフォローアップ:
  1. smart-pr の PR テンプレート（`assets/pr-template.md`）の「クラス / ファイル構成を表で一覧する」節は、本スキルの「変更ファイルの一覧は PR 本文に置かない」と食い違う。本スキルは smart-pr・smart-issue-resolve が PR 本文を書く場面でも読み込まれるため、最初に表に出る食い違いになる
  2. tech-doc-structuring の design-doc の見出しは「背景」から始まる。結論を先頭に置いた文書をこのスキルで整形すると、結論が後ろに移りうる
